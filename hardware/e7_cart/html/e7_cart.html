Running Custom Atari VCS Code on a vintage E7 Cartridge

Background

As a fun followup to my Apple II Myst demake I thought I would see how much of the game I could fit on an Atari 2600/VCS. Despite only being a limited subset of the game (though the full speedrun route is possible) this was a much more popular project and got a lot of press.

This was fun, and runs on real hardware, but by using a Harmony Cartridge or similar. This cartridge has a full 32-bit ARM processor in it and can read ROMs off of an SD-card. This is great for development, but not something that would have been available back in 1977 when the console debuted. In fact the ARM chip inside of it would have had workstation to supercomputing amounts of power back then. So I was wondering, could I get Atari 2600 Myst running using the actual technology of the time?

First some info on the E7 "Big Game" mapper from M-Network (Mattel). The Atari VCS/2600 has the 6507 processor in it, which is a 6502 chip but in a smaller package to save money. It only has enough address lines to access 8k of memory, but the Atari 2600 didn't bring all those pins out so the maximum you could address was 4k. Most early games were 2k or 4k ROMs, but that quickly turned out not to be enough so later various mapper schemes came up to bank-switch larger amounts of storage into the address space. At the time you could get up to 32k of ROM and usually by accessing special soft-switch memory addresses you could swap in ROM into the 4k region as needed. For Atari MYST I picked the E7 mapper not only because it could handle 16k of ROM, but also it in theory supported up to 2k of RAM. The Atari 2600 itself comes with only 128 bytes (yes, bytes) of RAM. To fit as many scenes from Myst as I could I wanted to use compression, but due to the race-the-beam nature of the graphics it would be much easier if I could decompress the graphics to a staging area bigger than 128 bytes. So that's what I did. The E7 supports up to 2k of RAM. A 1k region you can swap in instead of ROM, and also another 1k region you could swap in 256 bytes at a time. Getting RAM on a 2600 is a bit of a pain as it was only expected to use ROM so none of the read/write signals come out to the cartridge socket. So for this to work there is a hack where if you want to access 1k, you'll have two 1k regions, one for reads, one for writes. If you write to the write region your mapper is reponsible for setting up the signals to make sure writes happen. So in theory it was possible to support 16k of ROM and 2k of RAM in 1983 if you had access to this mapper. Where could I find some? It turns out there were three commercially released games that had E7 on board. Burgertime, Masters of the Universe, and Bump 'N' Jump. Burgertime is the only one of these that used the RAM functionality, so it seemed like a good source to get a chip.

Part 1: Desoldering a BugertTime cartridge

Just to be safe I acuired a bunch of Burgertime cartridges. There are two variants: one with through hole chips (Made in USA) and one with epoxy blobs for the E7 and ROM chips (Made in Singapore). I ended up with 6 cartriges. Only 3 of them actually ran the game, the others glitched or had other issues. In theory to play Myst on one of these it should be as simple as
  1. Replacing the ROMs with ones with my own code
  2. Upgrading the RAM from a 1k SRAM to 2k
It turns out in the end there was nothing simple about this. The ROMs are in the ZZZZZ pinout (used in IBM 5150 BIOS and Commodore 64) but that doesn't match the standard 27C64 8k EPROM format. You can get adapters, and I did from ZZZZZ but the footprint is too big to fit on the circuit board. The RAM is the Toshiba ZZZZZ which is nearly completely undocumented, even by Toshiba back in the day. It was used a few other places and it can be seen that the pinout is essentially the same as that of 6116 2k SRAM so the hope was one of those could be dropped in place. I made this monstrosity trying to grab the signals off the cart with the E7 in place and routing them to a breadboard. This was made difficult because my desoldering lifted a bunch of pads until I got a proper desolder gun instead of a suction pump. It didn't work. though someone suggested if I had added enough decoupling capacitors maybe it would. Then life got busy and that's where the project stood for 2 years.

Part 2: Custom PCB

I decided to pick this project back up. I fired up KiCAD and made a replica E7 cartridge, but with extra spacing to allow the ROM adapaters to fit, as well as bring out some of the pins for debugging. This was my first major project with KiCAD, previous had used gEDA and it took a bit of getting used to but worked out in the end. I mostly missed autorouting. I never used it for the whole project, but it was nice sometimes if you had a troublesome signal to see what the autorouter would do with it to help guide you. Sent it off then waited a few weeks for the boards to return. And the following steps
  1. Populate with all the chips from a known-good Burgertime to see if it worked. It did!
  2. Swap the ROMs with burned EPROM copies of Burgertime to see if the EPROM/ROM adapter worked. It did!
  3. Try updating the TZZZ RAM to 6116 2k. Sadly it glitched out. Oh no.
  4. Tried running a burnt copy of the MYST ROMs. The title screen worked but whenever it tried to hit the RAM it would glitch out.
ignore the extra large bypass caps, couldn't find smaller ones. Disappointing. But wasn't ready to give up. What could be keeping the ROMs from working. Worte an E7 tester ROM to put in and try to find out. Wasted time on a fancy splash screen. With the original 1k RAM in, it worked and all 4 banks of the 256k chunks seemed to work, but of course accessing the 1k not there didn't work. Alarmingly it would reset a lot when the ful 2k installed, almost like it was fighting the bus. The Toshiba chip the A10 line acts as an extra chip select so maybe if that's the case it might end up fighting things. So the E7 test that tried to write values to all of RAM then read it back just didn't work. The 256-byte chunks returned all zero and the other didn't seem to get the right values. I'm going to have to get some HW debugging to see what's happening
